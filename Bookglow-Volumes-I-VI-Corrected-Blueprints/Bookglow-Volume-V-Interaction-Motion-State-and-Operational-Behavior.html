Interaction, Motion, State & Operational Behavior

The behavioral contract for navigation, forms, booking, schedule, POS, feedback, realtime data and recovery.

The user should always know what changed, what is saved, what is still pending and what to do next.
Motion base80–320 ms
Critical writesServer-confirmed
Form modelExplicit save
RecoveryRetain context + retry
01 · Behavior mandate

The interface must make system state obvious before it makes the product feel animated.

Bookglow handles appointments, payments, balances and operational records. Interaction design therefore prioritises certainty, reversibility and visible state. Motion supports comprehension; it never hides delays or substitutes for feedback.

02 · State taxonomy

Use one vocabulary across customer and merchant surfaces.

StateMeaningVisual/behavioral contract
IdleReady for input.Clear affordance and no implied progress.
DirtyLocal edits differ from saved data.Save enabled; close warns when loss matters.
ValidatingChecking input/availability.Field or section progress without freezing unrelated controls.
SubmittingAuthoritative write in progress.Primary action disabled; duplicate submission blocked.
SuccessWrite confirmed.Persistent confirmation or updated record plus next action.
ErrorOperation failed.Plain-language message, retained input and retry.
Stale/conflictUnderlying data changed.Refresh affected choice and explain what changed.
Read-only/lockedRole or feature prevents mutation.Explain reason; do not imitate disabled loading.
03 · Navigation behavior

Route changes preserve orientation and prevent accidental state loss.

  • Active navigation derives from the URL, including nested member/integration routes.
  • Mobile More opens as a focus-managed sheet; selecting an item closes it and updates the route.
  • Booking Back returns one stage without discarding unrelated valid selections.
  • Direct booking stage URLs redirect to the earliest missing prerequisite.
  • Unsaved merchant forms warn before route/modal dismissal only when meaningful changes exist.
  • Browser back/forward works; important state is not trapped only in local component booleans.
04 · Selection behavior

Selections should be immediate, visible and reversible.

ControlBehavior
Service/professional/slotSingle selection; selected state uses border, icon and text.
Category/filterUpdates list immediately and preserves current selection only if still valid.
Payment methodSingle selection; total remains visible.
Appointment statusMay require confirmation for cancellation/completion; transitions reflect real rules.
Multi-item POS cartAdd immediately, edit quantity/staff inline or via compact sheet.
Bulk CRM actionsExplicit selection count and cancel/clear selection.
05 · Motion system

Use short, predictable transitions with reduced-motion support.

TokenDurationUse
Instant80 msPressed/active response.
Fast120 msHover, selection and compact state change.
Standard180 msCard/list reveal and route content fade.
Emphasis240 msMeaningful confirmation or layout reflow.
Overlay320 msSheet/modal entry and exit.
Avoid springy overshoot in POS, finance, settings and destructive flows. Operational UI should feel stable.
06 · Loading behavior

Show the shape of what is loading and keep the page stable.

  • Initial page load uses skeletons matching final rows/cards; avoid full-page spinner after the shell is known.
  • Button spinner appears inside the action and keeps its width stable.
  • Background refresh does not erase existing data; show subtle refresh state.
  • Booking availability cancels stale requests when date/service/staff changes.
  • Long operations expose progress or status text where possible.
  • No raw provider error appears in user-visible UI.

10 · Destructive actions

Make consequence, scope and reversibility clear.

  • Use specific verbs: “Delete member”, “Void sale”, “Cancel appointment”.
  • Describe linked impact when staff/member/service has related records.
  • Require typed confirmation only for unusually broad actions such as delete-all.
  • Prefer archive/deactivate where historical integrity requires records.
  • After success, return to a valid route and remove stale detail state.
11 · Booking journey behavior

Production booking requires authoritative checks and idempotent submission.

MomentRequired interaction
Service changesClear incompatible downstream state.
Professional changesReload availability and clear selected slot.
Date changesClear time immediately; show loading skeleton.
ReviewRevalidate availability in background or on submit.
Confirm clickCreate idempotency key, disable action and submit once.
ConflictKeep service/professional/details, return to refreshed date/time.
SuccessPersist only safe confirmation info; clear draft when “Book another” begins.
12 · Schedule behavior

Scrolling, date changes and status actions must remain predictable.

  • Sticky date controls remain anchored while appointment cards scroll.
  • Changing date updates the URL/query or stable page state and announces the result count.
  • Opening a booking preserves the scroll position when closed.
  • Status change shows immediate pending state and rolls back visually on failure.
  • Start POS transfers a single immutable appointment snapshot plus ID; the latest server data is checked before sale completion.
13 · POS behavior

Checkout is a transaction, not a collection of unrelated form fields.

  • Cart changes recalculate totals deterministically.
  • Member-required package rules block checkout with a precise explanation.
  • Staff/commission assignment remains visible at item or sale level according to current logic.
  • Completing sale locks the action until the authoritative write returns.
  • Receipt uses the confirmed transaction, not optimistic client values.
  • Failure keeps the cart intact and does not create partial points/voucher updates.

15 · Draft and persistence rules

Persist only what improves recovery without leaking data.

DataStorage rule
Booking merchant/service/professional/date/details draftSession-scoped, versioned and keyed by booking path; expire after a short period.
ConfirmationMinimal reference and display details; clear on new journey where appropriate.
Merchant filtersMay persist locally per user/outlet.
Unsaved sensitive form fieldsDo not persist broadly by default.
Admin override outletShow visible remote-view context and clear on logout/session end.
16 · Realtime and freshness

Realtime updates should preserve context, not make the interface jump.

  • Merge updates into stable lists using IDs.
  • Do not reorder while the user is editing unless the underlying sort key changes and the change is explained.
  • Show when a selected record was updated elsewhere.
  • Availability and appointment conflicts use server time and merchant timezone.
  • Provider subscriptions are created/cleaned behind repositories, not inside presentational cards.
17 · Network resilience

Design for intermittent mobile connectivity without pretending writes succeeded.

  • Read screens may show last known data with an “offline” indicator.
  • Financial, booking, points, voucher and status writes require server confirmation.
  • Retry uses idempotency where duplicate creation would be harmful.
  • Queued writes, if introduced, must show pending state and conflict policy.
  • Logout or outlet switch clears sensitive cached tenant data.
18 · Accessible interaction

Behavior remains understandable through keyboard and assistive technology.

  • Announce stage/page headings after navigation.
  • Use aria-live sparingly for selected slots, load results, save outcome and confirmation.
  • Calendar arrow-key behavior follows recognised grid patterns.
  • Focus never moves unexpectedly on realtime updates.
  • Reduced motion removes translation/scale while retaining necessary visibility changes.
  • Error summaries link to invalid fields on long forms.
