Platform Truth & Design-Retrofit Strategy

The authoritative boundary for redesigning the current Bookglow project while preserving all working data, calculations, permissions and workflows.

The experience layer changes. The operating logic does not.
ProgrammeDesign-first
RuntimeFirebase + Firestore
MethodIn-place retrofit
Backend migrationDeferred final stage
01 · Mandate

Redesign the product that exists—without changing the logic that already works.

This programme changes Bookglow’s design, user experience, layout, information hierarchy, responsive composition and component structure inside the current project. The existing application behavior is the protected core.

Locked rule: no replacement application, no parallel booking implementation, no backend rewrite and no business-logic refactor are part of Volumes I–VI.
02 · Current product truth

The current monorepo is the product and Firestore remains its working data layer.

AreaLocked current stateBlueprint treatment
RepositoryExisting monorepo with merchant portal and customer site.Edit both applications in place.
Customer bookingCurrent live booking routes and components.Redesign the live implementation directly.
Merchant operationsDashboard, schedule, POS, members, inventory, staff, reports, finance, marketing and settings.Preserve all handlers and reorganise presentation page by page.
Authentication and dataFirebase authentication and Firestore are wired and working.Continue using them unchanged throughout this design programme.
Business logicThe user has confirmed that existing logic is correct.Treat calculations, permissions, listeners, writes and workflows as non-editable unless a separate bug task is opened.
Future backend workDatabase migration and Firebase removal are deferred.Create a separate final-stage migration blueprint only after the complete design retrofit is stable.
03 · Product definition

Bookglow is one service-business operating system with two coordinated experiences.

1

Customer experience

A merchant-owned storefront and guided booking journey that helps customers select, understand and confirm an appointment.

2

Merchant workspace

A practical operating environment for appointments, checkout, members, inventory, staff, reporting and configuration.

3

Shared product language

One governed Bookglow design system connects both applications without forcing them to have identical density.

06 · Experience principles

Five principles govern every design decision.

01
Useful before decorativeThe first useful action or information appears before promotional or secondary content.
02
One dominant actionEvery screen and temporary surface establishes one clear next action.
03
Mobile composition, not compressionMobile layouts reorder and regroup content rather than shrinking desktop screens.
04
Dense but calmOperational screens show more useful information without creating visual noise.
05
Behavior remains stablePresentation changes must not alter state ownership, data flow or business outcomes.

08 · Logic preservation contract

The following behavior is protected during every page retrofit.

  • Firebase authentication and all existing login/registration handlers.
  • Firestore queries, listeners, writes, collection paths and document fields.
  • Booking availability, submission and confirmation logic.
  • Appointment creation, editing, cancellation and status transitions.
  • POS cart, totals, discounts, taxes, payment and transaction creation.
  • Members, points, credits, vouchers and outstanding balances.
  • Inventory, products, services, packages and stock behavior.
  • Staff, schedules, roles, permissions and commissions.
  • Reports, finance, expenses and export calculations.
  • Routes, redirects, persisted storage keys and environment contracts.

10 · Success measures

The redesign succeeds when work becomes easier without changing outcomes.

DimensionMeasure
Mobile usabilityPrimary workflows complete at 360–375 px without normal horizontal scrolling.
Operational densityMore relevant bookings, products, members or transactions are visible per viewport.
ClarityEvery page has a clear title, status, primary action and next step.
ConsistencyShared components and semantic tokens replace page-specific visual inventions.
SafetyThe same handlers, data writes, calculations and permission outcomes remain intact.
AccessibilityKeyboard focus, labels, contrast, touch targets and state announcements meet the agreed standard.
11 · Risk control

The largest risk is accidentally mixing design work with logic work.

RiskControl
Large-page refactor changes state behavior.Extract presentational components only and keep effects/handlers in the current container.
Visible rename breaks persisted data.Change display copy only; preserve technical identifiers.
Mobile cleanup hides features.Create a feature inventory before editing and verify every prior action afterwards.
Backend migration distracts from design.Keep Firestore/Firebase unchanged; defer migration to a separate final programme.
Several pages are changed at once.Release and verify page by page.
12 · Locked decisions

These decisions carry through every later volume.

01
Current source remains authoritativeNo new application or alternative implementation is introduced.
02
Firestore-first operation continuesThe present backend and authentication stack remain untouched.
03
Design is the programme priorityUI, UX, layout, structure, responsiveness and accessibility are the work.
04
Logic is treated as correctNo business rule changes are permitted inside this programme.
05
Future migration is separateAny future Firestore-to-Supabase migration and Firebase removal happen only after this programme, under a new blueprint.
06
Verification is requiredA page is complete only when its old behavior and new presentation both pass.
