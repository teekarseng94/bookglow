Existing-project retrofit · Volume VI

Existing-Code Implementation & Supabase V2 Transition

A file-level, reversible implementation plan that upgrades the current monorepo, finishes Booking V2 and later moves the source of truth to Supabase.

Do not rebuild Bookglow. Make the current project become Bookglow V2 through controlled replacement from inside.
Immediate sequenceBaseline → UI foundation
Booking strategyFinish existing V2
Merchant strategyPage-by-page retrofit
Final data targetSupabase
01 · Implementation mandate

Transform the current project through reversible slices.

This volume is the build order. It deliberately separates visual retrofit, functional parity and data-provider migration. Each phase has a rollback point and a definition of done. The result remains the same monorepo and the same product routes.

Never delete the live booking page, Firebase services or current deployment configuration before the replacement path passes production-parity gates.

12 · Phase 6 · Prepare provider-neutral repositories

Remove Firestore from UI boundaries before switching providers.

domain types + repository interfaces ↑ merchant hooks / booking adapters ↑ FirestoreRepository (legacy runtime) | SupabaseRepository (V2 target) ↑ contract tests assert equivalent behavior
  • Rename useFirestoreData to a provider-neutral domain hook after its internals are abstracted.
  • Move remaining direct Firestore imports from customer V2 and merchant hooks/services behind repositories.
  • Define canonical field names and mapping once; do not spread camelCase/snake_case conversions across screens.
  • Make subscriptions, transactions and idempotent writes part of the repository contract.

15 · Security hardening

Tenant isolation and public-data projection are release blockers.

  • No super-admin identity may be hardcoded in frontend code.
  • Every authenticated query derives outlet access from server-verified membership/claims.
  • Public booking reads only a public projection—never staff contact details or internal settings.
  • Service role keys never enter browser bundles.
  • API keys/webhooks are stored and revealed according to one-time-secret rules.
  • Cross-tenant tests attempt read, write, realtime and storage access.
  • Logs and analytics avoid customer-sensitive form content.

17 · Performance and build

Do not let the retrofit increase operational latency.

  • Retain lazy-loaded merchant pages and Booking V2 chunking.
  • Split the large marketing App into route/section chunks where useful.
  • Optimise merchant cover, staff and service images.
  • Avoid importing both Firestore and Supabase clients into the active bundle before cutover.
  • Measure list rendering for large CRM/transaction datasets; virtualise only when evidence requires it.
  • Set performance budgets for initial JS, route chunk and image payloads.

20 · Definition of done

The blueprint is complete only when the existing project becomes the target product.

  • No parallel replacement app exists.
  • Live /book uses the completed Booking V2 journey with real availability and booking creation.
  • Merchant core pages are fully usable at 375 px and desktop.
  • All navigation resolves correctly; orphan/duplicate routes are addressed.
  • Bookglow naming is consistent in visible product copy.
  • Supabase is the validated primary source of truth; Firebase is legacy migration/rollback only.
  • Critical business and tenant-security tests pass.
  • Deployment, monitoring and rollback procedures are documented and exercised.

22 · First implementation move

Begin with baseline and the shared UI foundation—then finish Booking V2.

The immediate work sequence is: create the baseline evidence, reconcile customer V2 tokens, build merchant UI primitives, and connect real availability/submission to the existing Booking V2. This creates visible progress without risking current operations.
