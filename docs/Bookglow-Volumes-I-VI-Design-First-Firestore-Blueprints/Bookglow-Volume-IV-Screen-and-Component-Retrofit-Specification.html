Screen & Component Retrofit Specification

The target layout and component composition for every current Bookglow screen, from public booking through merchant operations.

Reorganise every current capability into a clearer structure—do not replace the capability.
ScopeAll current screens
MethodIn-place
MobileRecomposed
LogicUntouched
01 · Retrofit rule

Every screen is edited in place and accepted only when its existing function still works.

Volume IV defines the target composition of the current screens. It is a layout and component specification, not a replacement implementation.

Locked: every current button, handler, permission, calculation, data operation and route must remain available after the redesign.
02 · Global application shells

Standardise shared structure before page-level polish.

ShellRequired structure
Merchant desktopGrouped sidebar, compact utility header, active page context and responsive content frame.
Merchant mobileCompact page header, bottom navigation for primary work and a More sheet for secondary destinations.
CustomerMerchant-first masthead, focused booking content, mobile sticky action and restrained Bookglow attribution.
AuthenticationClear product identity, focused form and concise supporting proof.
03 · Marketing and acquisition

Make public pages describe the product the portal actually delivers.

  • Hero states the product outcome and one primary action.
  • Feature sections correspond to real merchant capabilities.
  • Pricing and integrations use consistent visual structure.
  • Registration preserves all existing authentication handlers.
  • Remove unrelated stock imagery and false functionality claims.
04 · Booking storefront

Confirm merchant identity without consuming the first mobile viewport.

ElementSpecification
CoverResponsive, compact on mobile and focal-point aware.
Logo/nameProminent but not oversized.
ContextLocation, operating status and concise merchant details.
Deferred detailsHours, policies, contact and about content in expandable sections.
First useful contentService categories or first service card visible in the first mobile viewport.
05 · Service selection

Make the catalogue scannable before expressive.

  • Category chips remain compact and horizontally scrollable when needed.
  • Service name is primary; description is clamped.
  • Duration and price are always visible.
  • The whole card is interactive while preserving the current selection callback.
  • Unavailable services explain their state instead of disappearing.
06 · Professional selection

Lead with availability, then preference.

  • Any available is the first explicit option where current logic supports it.
  • Staff cards show name, role/speciality and availability context.
  • Missing photos use initials, not random stock faces.
  • Selection is visible beyond colour.
  • Current staff-selection handlers remain unchanged.
07 · Date and time

Present existing availability clearly without changing its source or calculation.

SlotsConsistent grid, local time formatting and clear selection.
No availabilityKeep earlier choices and make another date easy to select.

08 · Details, review and confirmation

Make commitment and system outcome unmistakable.

StageRequired structure
DetailsPersistent labels, concise helper text, current validation and one next action.
ReviewMerchant, service, staff, date, time, customer details, price and policy summary.
SubmittingDisable duplicate submission using the current submission state.
ConfirmationReference, complete booking details and useful next actions.
FailureSpecific error and retry without clearing valid data.
09 · Dashboard / Today

Make the first merchant screen an operational briefing.

  • Top section answers what is happening today.
  • Needs-attention items precede secondary analytics.
  • Upcoming bookings and current sales are visible without equal-weight card clutter.
  • Charts remain secondary to actionable information.
  • All existing metrics and navigation callbacks remain.

12 · Members and member details

Increase density while making customer value easier to understand.

  • Member list rows show identity, status and one meaningful value or activity indicator.
  • Search and add-member action remain visible.
  • Filters move to a sheet on mobile.
  • Member details group profile, visits, points, credits, vouchers and balances.
  • Existing histories, edits and financial member actions remain.

14 · Staff and team

Make people, schedules, permissions and commissions understandable.

  • Dense roster cards/rows show name, role, status and next useful information.
  • Editor separates profile, schedule, permissions and commission sections.
  • Operating schedules use compact day rows.
  • Mobile editor uses a focused panel with sticky save.
  • Existing upload, permission and commission logic remains.
15 · Sales history, reports and finance

Use one responsive reporting language.

  • Desktop tables retain useful comparison.
  • Mobile replaces wide tables with structured transaction/report rows.
  • Amount, customer, date/time, payment method and status lead each row.
  • Secondary detail opens in the current modal or a responsive sheet.
  • Filters, date ranges, exports, chart data and calculations remain unchanged.
16 · Settings, marketing and integrations

Group configuration by responsibility and save boundary.

SectionContent
Business profileName, contact, location and visible identity.
Booking pagePublic link, customer theme and booking settings.
Operating hoursCompact day rows; mobile stays on one row where possible.
NotificationsReminders and communication settings.
Receipt and paymentCurrent receipt/payment configuration.
IntegrationsExisting third-party connections.
AdvancedLower-frequency or technical settings.
Save rule: retain the current explicit-save or auto-save behavior exactly; the redesign may improve feedback but must not invent a new persistence model.
17 · Super admin

Separate platform oversight from merchant operation.

  • Use a distinct platform context and permission gate.
  • Subscribers/outlets use responsive tables or rows.
  • Platform actions require explicit confirmation.
  • Do not expose super-admin navigation to merchant users.
