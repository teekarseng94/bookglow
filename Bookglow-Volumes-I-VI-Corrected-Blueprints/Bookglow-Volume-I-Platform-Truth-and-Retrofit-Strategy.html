Platform Truth & Retrofit Strategy

An audited foundation for improving the current Bookglow monorepo without replacing its working customer, merchant or operational systems.

The current product is the foundation. The blueprint changes its experience layer in controlled, reversible phases.

01 · Mandate

Improve the product that exists—do not replace it.

This volume establishes the audited product truth and the rules for changing Bookglow safely. The project is already a working two-app SaaS with customer booking, merchant operations, Firebase production dependencies and a partially built Booking V2. The programme is therefore a controlled retrofit, not a greenfield rebuild.

Locked rule: no second repository, no replacement application and no duplicate “new platform” may be created. Every phase must modify, extract, replace or retire code inside the current monorepo.

03 · Product definition

Bookglow is one service-business operating system with two primary faces.

01

Customer experience

Marketing, merchant discovery, public booking, optional customer identity, voucher purchase/redemption and booking confirmation.

02

Merchant workspace

Daily schedule, checkout, members, services/products/packages, staff, revenue, expenses, marketing, integrations and settings.

03

Platform governance

Multi-tenant outlet isolation, roles, super-admin operations, public data boundaries, auditability and future Supabase ownership.

Product promise: help service businesses get booked, operate the day, get paid and retain customers from one calm system.

07 · Experience pillars

Four principles govern all retrofit decisions.

01
Useful on the first screenEvery page exposes the next operational decision before decorative or secondary content.
02
Mobile is a working environmentThe merchant portal is not merely responsive; core daily tasks must be comfortably executable at 375 px.
03
Merchant-owned, Bookglow-governedMerchant identity leads the customer storefront while layout, accessibility and transaction behavior remain controlled.
04
Change without operational disruptionVisual changes and data-provider changes are separated so defects are diagnosable and rollbacks remain possible.

12 · Data truth

Supabase is the V2 target, but Firestore is still the active runtime today.

Current fact: the active merchant provider exports Firestore services and declares DB_PROVIDER = firestore. The Supabase layer is not yet used by the running application.
01

During UI retrofit

Keep all reads/writes through current working services. Introduce visual and component changes without changing persistence behavior.

02

During provider preparation

Define typed repository contracts, remove direct Firestore imports from screens/hooks and make both providers pass contract tests.

03

During cutover

Make Supabase the primary source of truth, use Firebase only as migration input/temporary rollback, and validate tenant isolation.
