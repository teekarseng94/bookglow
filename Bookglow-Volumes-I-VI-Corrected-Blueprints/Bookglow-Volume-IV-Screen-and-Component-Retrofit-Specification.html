Screen & Component Retrofit Specification

A route-by-route specification for upgrading the current customer site and merchant portal while preserving their working logic.

Every approved screen maps to a current route, component and acceptance gate—never to a replacement application.
Customer stages6 + edge states
Merchant modulesCurrent routes preserved
Mobile baseline375 px
Build methodIn-place extraction
01 · Retrofit rule

Each screen is edited in place and accepted only when its existing function still works.

This volume is the screen-by-screen build specification. It maps directly to current source files and routes. “Redesign” means reorganising presentation around proven handlers and services—not recreating the feature in a new page.

Do not copy a page into a “V2” sibling inside the merchant portal. Refactor the existing route component or extract reusable presentation components from it.

11 · Confirmation stage

Show an operational confirmation, not a celebratory dead end.

  • Display real appointment reference, merchant, service, date, time and professional preference.
  • Show address map and phone actions when available.
  • Explain reminder/contact expectations and cancellation policy.
  • Offer “Add to calendar”, “Book another” and optional account/history action.
  • Never display the preview badge or preview reference prefix in production.

15 · Schedule

Optimise the most time-sensitive page for touch and scrolling.

  • Sticky compact date strip/header while appointment list scrolls.
  • Date click opens an accessible calendar sheet.
  • Appointment cards prioritise time, customer, service, staff and status in two or three rows.
  • Details open in a mobile full-screen sheet / desktop side panel.
  • Status actions are explicit and destructive transitions require confirmation.
  • “Start POS sale” carries appointment context into POS exactly once.
  • Preserve Setmore sync and reminder behavior behind existing handlers.

17 · Members / CRM

Increase list density without hiding customer value.

  • Mobile rows show name, phone, points/credit/voucher/outstanding summary in two to three compact rows.
  • Search and key actions remain sticky/visible.
  • Add/edit forms use one save action and never depend on keyboard submit.
  • Import/export, duplicate detection and undo-import keep existing logic and receive clear progress states.
  • Bulk delete remains high-friction and role/feature locked.

19 · Menu / Inventory

Use compact entity cards and one editing pattern for services, products and packages.

  • Tabs or segmented control clearly identify services/products/packages.
  • Category order remains draggable on suitable screens with accessible alternative controls.
  • Mobile entity cards use a compact 2–3 row layout, not four large rows.
  • Image, name, category, price/duration/stock and status are immediately scannable.
  • Editing opens a consistent sheet/modal with fixed Save; closing without save never silently writes.
  • Locked features explain why editing is unavailable.
20 · Staff & Team

Make people and commission settings understandable on mobile.

  • Compact roster cards with photo/initials, name, role and qualified service count.
  • Edit form uses visible Save and upload progress.
  • Role commission configuration is separated from individual profile editing.
  • Delete requires impact warning when appointments/transactions reference the staff member.
  • Image size/type validation remains explicit.

22 · Marketing, settings and integrations

Consolidate configuration into clear sections and save boundaries.

  • Marketing shows voucher campaigns/status and public links without mixing unrelated operational settings.
  • Settings groups Business profile, Booking page, Hours, Payments, Reminders, Access and Integrations.
  • Mobile operation-hour rows stay on one compact line where possible.
  • Every section has explicit save status; do not rely on modal close to persist.
  • Booking URL copy/share controls use the canonical customer-site URL.
  • API keys are never shown again after the one-time reveal unless regenerated.
23 · Super admin

Separate platform oversight from merchant operation.

  • Use durable role/claim-based access instead of a hardcoded owner email.
  • Show platform metrics, subscribers and outlet status.
  • Remote outlet viewing must display an unmistakable banner and exit action.
  • Never mix merchant bottom navigation with platform admin routes.
