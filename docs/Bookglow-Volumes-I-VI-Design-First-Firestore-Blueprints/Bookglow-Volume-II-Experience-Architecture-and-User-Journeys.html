01 · Mandate

Make every current route part of one understandable journey.

Volume II reorganises the experience around user goals. It does not change the logic behind those routes, actions or data.

Journey rule: preserve the current route and handler ownership; improve orientation, hierarchy and continuity around it.
02 · Experience model

Bookglow has three connected journeys.

1

Acquire

A merchant understands Bookglow and reaches registration.

2

Book

A customer recognises the merchant, chooses an appointment and receives confirmation.

3

Operate

A merchant or staff member runs the workday from schedule through payment and retention.

03 · Customer booking journey

One decision dominates each stage.

StagePrimary questionDesign outcome
Merchant contextAm I booking the correct business?Compact identity, location and operating context.
ServiceWhat do I want?Scannable categories and service rows with duration and price.
ProfessionalDo I want anyone or a specific person?Availability-first choice with optional preference.
Date and timeWhen can I come?Clear calendar, explicit availability and selected slot.
DetailsWhat does the merchant need from me?Short, labelled form with validation.
ReviewWhat am I committing to?Complete summary, policies and one confirmation action.
ConfirmationWhat happens next?Reference, merchant, date/time and useful next actions.
04 · Booking state continuity

The current live booking state remains the single owner.

  • Do not duplicate selection state in extracted visual components.
  • Back navigation should preserve valid earlier choices.
  • Changing an earlier choice clears only downstream values that are no longer valid.
  • Loading and error surfaces must not erase entered customer details.
  • A mobile sticky action summarises the current choice without duplicating the full desktop summary.

07 · Role journeys

Permissions affect both visibility and action availability.

RuleRequired behavior
NavigationDo not show destinations the user cannot use.
ActionsA hidden navigation item is not sufficient; existing permission checks remain on actions.
Empty statesDo not present permission denial as missing data.
Shared devicesKeep user/outlet context visible enough to prevent wrong-account actions.
08 · Cross-surface continuity

Merchant configuration should be visible in the customer experience.

  • Merchant name, logo, cover, address, status and safe accent appear consistently.
  • Services, professionals, operating hours and availability shown to customers reflect existing merchant data.
  • Customer wording remains merchant-facing while system errors remain Bookglow-governed.
  • Customer pages never expose private merchant operational data.
09 · Customer identity

01

02
Recognisable returnWhere existing logic supports it, previous details may be reused transparently.
03
Clear consentIdentity, marketing consent and booking submission are separate decisions.
04
Preserve current handlersDo not change authentication providers or redirect contracts in this programme.
10 · Recovery architecture

Every dead end has a useful next action.

ConditionRecovery
Merchant not foundExplain the link problem and provide a safe way back.
No servicesExplain online booking is unavailable; show merchant contact only when current data provides it.
No availabilityPreserve service/staff choice and make date change easy.
Submission conflictRefresh availability, explain the conflict and keep customer details.
Network failureRetain the current form and offer retry.
Permission deniedExplain access limits without exposing restricted data.
11 · Responsive journey rules

Recompose the same task for each viewport.

ViewportJourney composition
MobileSingle task column, sticky action, sheets for focused choices and compact lists.
TabletBalanced columns where they aid comparison; keep touch-first behavior.
DesktopPrimary work column plus summary, filters or detail rail where useful.
Wide desktopUse a maximum content width; never stretch forms and cards indefinitely.
12 · Accessibility journey

The complete journey must work without hover or precise pointer input.

  • Logical heading order and landmarks.
  • Keyboard path through navigation, selection, forms and overlays.
  • Visible focus and explicit selected states.
  • Announcements for loading, errors, saving and confirmation.
  • Back, close and cancel behavior that does not trap focus or lose work.
13 · Volume II acceptance

A journey is complete when purpose, action and recovery are clear.

CheckAcceptance
OrientationThe user knows where they are and which merchant/outlet/account is active.
Primary actionOnly one action visually dominates the current state.
ContinuityValid prior input survives navigation and recoverable failures.
Role fitNavigation and actions match the existing permission model.
Mobile fitThe task completes without desktop-only interaction.
Logic safetyThe same existing callbacks and data paths are used.
