01 · Design mandate

Use the already-defined UI/UX direction as the governed visual layer for the current code.

The supplied Volume III established a merchant-owned, Bookglow-governed and booking-first visual system. This corrected version keeps that direction and maps it to both current applications, including the existing Booking V2 token files and the merchant portal Tailwind implementation.

This volume does not propose another visual concept. It turns the approved UI/UX into a practical retrofit system.
02 · Dual-surface design

Customer calm and merchant efficiency share foundations but not density.

01

Customer storefront

Warm, calm, merchant-led and focused on one decision per stage. More breathing room and stronger identity moments.

02

Merchant workspace

Operational, compact and highly scannable. Information density is higher, but touch targets and hierarchy remain clear.

03

Shared foundation

Typography roles, semantic colours, spacing scale, focus, controls, feedback, icons and motion vocabulary.

06 · Merchant theme engine

Accept a small set of identity inputs and derive safe interaction roles.

01

Merchant controls

  • Logo
  • Cover image and focal point
  • One accent colour
  • Short public description
02

Derived automatically

  • Action hover/active
  • Readable action text
  • Soft selection surface
  • Subtle border
  • Focus treatment
  • Fallback initials tile
03

Not supported

  • Custom fonts
  • Free-form page backgrounds
  • Merchant-controlled error colours
  • Arbitrary button styles
  • Dark mode at launch
The theme engine must validate contrast and fall back safely; raw merchant hex values must never be consumed directly by components.

11 · Iconography

One outline family, with text carrying the meaning.

  • Use Lucide React or one equivalent family consistently.
  • 16 px for metadata, 20 px for controls, 24 px for primary status.
  • Use icon + label for unfamiliar actions.
  • Icon-only controls require an accessible name and adequate target size.
  • Do not mix emoji, filled illustrations and outline icons inside transactional flows.

15 · Navigation design

Navigation should reflect task priority, role and current location.

  • Desktop sidebar groups daily work, catalogue/people, performance and setup.
  • Mobile bottom navigation contains four primary tasks plus More.
  • Active route remains visible when viewing a nested page such as member details.
  • Schedule may use its own compact header but must retain access to global navigation.
  • Do not show pages the role cannot use; do not merely disable every control after entry.

17 · Accessibility

Accessible behavior is part of the component contract.

  • WCAG 2.2 AA contrast target.
  • Minimum 44 × 44 px interactive target.
  • 16 px mobile form controls to avoid browser zoom.
  • Focus order follows visual order; focus returns after modal close.
  • Errors connect to fields with aria-describedby.
  • Live regions announce loading, selection and confirmation without excessive repetition.
  • Reduced-motion preferences neutralise nonessential transitions.

19 · Anti-patterns

Visual choices that would weaken the retrofit.

01

Full-page merchant colour

Reduces readability and makes transactional states ambiguous.

02

Oversized mobile hero

Pushes services or daily work below the fold.

03

Card inside card inside card

Creates noise and wasted vertical space.

04

Colour-only state

Fails accessibility and weakens clarity.

05

Desktop table squeezed onto phone

Creates horizontal scrolling and hidden actions.

06

Animation as premium

Motion must explain state, not decorate every interaction.
