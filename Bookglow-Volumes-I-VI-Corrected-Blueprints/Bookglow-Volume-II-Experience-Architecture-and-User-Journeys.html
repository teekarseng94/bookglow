01 · Mandate

Make every route part of one understandable journey.

The existing repository contains rich functionality, but it grew across separate apps, duplicate booking surfaces and mixed route conventions. This volume defines the intended experience architecture without changing the product boundary established in Volume I.

The journey blueprint is implementation-aware: every stage maps to current routes, state, services and page files.
02 · Experience model

Bookglow has three connected journeys, not two disconnected websites.

01

Merchant acquisition

Understand Bookglow → review capabilities/pricing → sign up → reach merchant onboarding/login.

02

Customer booking

Recognise merchant → choose service → choose professional preference → choose date/time → provide details → review → confirm.

03

Merchant operation

Open Today → manage schedule → check out in POS → update members/menu/staff → review performance → configure outlet.

Date/timeSelected ISO date and slotChanging date clears time; slot is never trusted after expiry.

10 · Customer identity

Guest booking remains the default; identity adds convenience, not friction.

01
Do not force login before service discoveryThe public route must remain immediately useful.
02
Preserve booking state through optional authReturning from auth should restore the same merchant and valid selections.
03
Use phone as an operational contact fieldValidation and formatting should match merchant country context.
04
Avoid duplicate customer recordsServer-side matching rules should be deterministic and merchant-scoped.
05
Keep private history privateA customer may access only their own bookings and profile after verified identity.
11 · Availability journey

Availability is a live operational fact, not decorative calendar UI.

MomentRequired behavior
Date opensLoad business status and slots for service, duration and selected professional preference.
Slot selectedHold selection in client state but do not promise it is booked.
Review opensRevalidate the selected slot or clearly ask the customer to choose another.
SubmitCreate appointment atomically and reject conflicts.
ConflictReturn to date/time with preserved upstream choices and an understandable message.
Network failureKeep the selection, allow retry and avoid duplicate appointment creation.

  • Bottom navigation in portal
  • No horizontal data tables for core tasks
02

  • Schedule retains touch-first controls
  • Side drawers may replace full-screen sheets
03

  • Persistent sidebar
  • Booking summary rail
  • Denser report layouts
  • Hover only as enhancement, never as sole cue
14 · Accessibility journey

Navigation and state guards must work without sight, hover or precise pointer control.

  • Logical heading hierarchy and landmarks on every route.
  • Visible keyboard focus and 44 px minimum touch targets.
  • Route changes announce the new stage/page.
  • Selected, unavailable, error and success states use text/icon/shape—not colour alone.
  • Calendar supports keyboard navigation and an equivalent list-based mental model.
  • Modals and sheets trap focus, restore focus and close predictably.
15 · Data boundaries

Screens consume domain adapters; provider-specific code stays behind them.

Customer screens → publicBookingAdapter / availabilityRepository / bookingSubmissionRepository Merchant pages → typed domain services / repositories Repositories → Firestore today, Supabase after validated cutover No screen → direct Firestore or Supabase query in the target architecture
