Existing-Code UI Retrofit & Logic Preservation

The page-by-page implementation plan for applying Volumes I–V safely to the current source without backend or business-logic changes.

Change structure and presentation in small slices. Keep every existing behavior wired to the same owner.

01 · Implementation mandate

Transform the current presentation through reversible, page-level slices.

Volume VI converts Volumes I–V into a safe build sequence. It is exclusively a design and front-end structure programme around the current working logic.

Out of scope: backend migration, Firebase removal, Firestore abstraction, domain rewrites and business-rule changes. Those belong to a separate final-stage programme after design completion.
02 · Code truth

Build from the current architecture and current live components.

AreaImplementation rule

Page containersKeep state, effects, permissions, service calls and handlers.
Presentational JSXMay be extracted into reusable components.
StylesMove toward shared semantic tokens and primitives.
DataKeep Firebase authentication and Firestore code unchanged.
Removed/obsolete systemsDo not restore parallel implementations.
03 · No-new-app and no-new-logic rules

Refactor boundaries prevent another project from appearing inside the project.

  • Do not create a second booking implementation.
  • Do not create replacement merchant pages under new routes.
  • Do not introduce duplicate state stores for visual components.
  • Do not add mock data to replace real data.
  • Do not rename persisted fields or storage keys for aesthetics.
  • Do not move service calls merely to make folders look cleaner.

05 · Phase 1 · Design foundation

Establish shared tokens and primitives without changing behavior.

  • Global reset, typography and accessibility defaults.
  • Semantic colour, spacing, radius, border and elevation tokens.
  • Button, field, badge, alert, skeleton, sheet, modal and sticky-action primitives.
  • PageHeader, FilterToolbar, DenseEntityRow and state surfaces.
  • No page-specific business behavior moves into primitives.

07 · Phase 3 · Current customer experience

Apply Volumes II–V directly to the live booking implementation.

  • Redesign merchant header/storefront.
  • Recompose service, professional, date/time, details, review and confirmation stages.
  • Extract presentation only where it reduces complexity.
  • Keep current booking state, availability and submission logic untouched.
  • Verify guest booking, authentication redirects, errors and mobile sticky actions.

13 · Performance and build

Optimise only after visual and behavior parity are stable.

  • Measure production bundles before changes.
  • Use route-level lazy loading for genuinely secondary pages.
  • Defer heavy charts, integrations or AI code where safe.
  • Optimise images and remove confirmed dead imports.
  • Do not combine performance changes with logic rewrites.

15 · Future backend programme

Database migration is intentionally outside Volumes I–VI.

Continue operating on Firebase authentication and Firestore throughout this complete design programme. Only after every page, interaction and responsive structure is stable should a separate migration blueprint be created to move Firestore data to Supabase and later remove Firebase safely.

Do not prepare, partially activate or mix that migration into the current design implementation.
16 · Definition of done

The design programme is complete when the existing project has become the approved experience.

  • No parallel or replacement implementation exists.
  • All current customer and merchant screens follow Volumes II–V.
  • Primary workflows are fully usable at 360–375 px, tablet and desktop.
  • Visible design and branding are consistent.
  • Every existing feature remains accessible and functional.
  • No Firestore/Firebase behavior was changed.
  • Build, type, accessibility and regression verification are documented.
  • Future backend migration remains a separate final-stage project.
