01 · Behavior mandate

Make system state obvious without changing the business behavior underneath it.

Volume V defines how the redesigned interface communicates and responds. Existing state variables and handlers remain the source of truth.

Rule: improve feedback around the current operation; do not create a second save, booking, checkout or permission pathway.
02 · State taxonomy

Use one vocabulary across customer and merchant surfaces.

StateMeaning
LoadingData is being fetched and no result is available yet.
RefreshingExisting data remains visible while freshness updates.
EmptyThe operation succeeded but no records exist.
UnavailableA known choice cannot currently be selected.
SavingA write is in progress.
SuccessThe intended operation completed.
WarningAction is possible but deserves attention.
ErrorThe operation failed and requires recovery.
ConflictThe selected data changed or is no longer valid.
03 · Navigation behavior

Preserve orientation and unsaved work.

  • Active route and page title stay visible.
  • Back behavior returns to the expected prior context.
  • Closing a sheet or modal does not trigger unrelated navigation.
  • Unsaved changes use the current persistence model and an explicit warning where necessary.
  • Role restrictions remain enforced by existing guards.
04 · Selection behavior

Selections are immediate, visible and reversible.

01
Use the whole row/card where safeThe existing callback is invoked from one clear interactive target.
02
Show selected state beyond colourAdd check, border or explicit wording.
03
Preserve dependent logicChanging a selection follows current downstream reset rules.
04
Explain unavailabilityDo not silently hide important options.

Use short, predictable transitions with reduced-motion support.

06 · Loading and refresh

Keep layout stable and distinguish first load from refresh.

  • Skeletons approximate the final content shape.
  • Buttons preserve width during saving.
  • Existing content remains during refresh when safe.
  • Do not show empty state while data is still loading.
  • Long operations show meaningful progress or a persistent status.
07 · Success, warning and error feedback

Match persistence to consequence.

ConsequenceFeedback
Small reversible editInline confirmation or brief toast.
Record creation/updatePersistent success near the action plus updated content.
Booking or paymentDedicated confirmation state with reference/details.
Validation issueInline message associated with the field.
System failurePersistent error with retry or safe exit.
Destructive actionConfirmation before action and outcome afterwards.
08 · Form behavior

Every form has a clear save lifecycle.

  • Persistent labels and correct input modes.
  • Validation after blur or submission using current rules.
  • Never clear valid values after an error.
  • Save action reflects idle, saving, success and failed states.
  • Mobile sticky save remains above browser/navigation chrome.
  • Do not convert explicit save into auto-save or vice versa.
09 · Modal, drawer and sheet behavior

Choose the temporary surface according to task size and viewport.

SurfaceUse
PopoverSmall, noncritical choice.
ModalFocused confirmation or short form.
Side drawerDesktop detail or editing with context preserved.
Bottom sheetMobile selection, detail or editing.
Full pageComplex workflow that needs route history.
  • Trap focus inside modal/sheet.
  • Return focus to the invoker.
  • Support Escape where appropriate.
  • Avoid stacking multiple overlays.
10 · Destructive actions

Make consequence and scope clear.

  • State exactly what will be deleted, cancelled or disconnected.
  • Use current permission checks.
  • Do not place destructive action beside the primary save without separation.
  • Require confirmation for irreversible operations.
  • Preserve any existing undo or recovery behavior.
11 · Booking behavior

The current booking flow must feel trustworthy at every stage.

  • Availability loading is explicit.
  • A selected slot remains visible in the summary.
  • Submission prevents duplicate action using current state.
  • Conflict keeps customer details and asks for another slot.
  • Confirmation shows complete operational details.
  • Current booking API and Firestore behavior remain unchanged.
12 · Schedule behavior

Scrolling, date changes and booking actions remain predictable.

  • Sticky date controls do not cover content.
  • Changing date preserves the selected view.
  • New or updated bookings appear without jumping the user unexpectedly.
  • Opening detail preserves scroll position.
  • Current create/edit/status/cancel handlers remain.
13 · POS behavior

Checkout presents one transaction with one clear completion action.

  • Cart modifications update the existing calculated totals.
  • Payment choices remain subordinate to the final checkout action.
  • Saving prevents accidental duplicate transaction creation.
  • Success clearly identifies completion and next action.
  • Failure keeps the cart and customer selection intact where current logic does.
14 · Members, inventory and staff behavior

Lists and editors use the same state language.

PatternBehavior
Search/filterResults update without losing page context.
Editor openCurrent selected entity populates the existing form state.
SaveUse current callback; show lifecycle around it.
DeleteUse current confirmation and permission behavior.
Realtime changeUpdate content without closing the editor or resetting filters unnecessarily.
15 · Network resilience

Do not pretend a write succeeded.

  • Show an explicit offline or connectivity state where detectable.
  • Keep entered data during retry.
  • Do not invent an offline write queue unless one already exists.
  • Differentiate permission, validation and network failures when current errors allow it.
16 · Accessible interaction

Behavior remains understandable through keyboard and assistive technology.

  • Focus moves to the first invalid field after failed submission.
  • Live regions announce saving, failure and confirmation appropriately.
  • Icon-only actions have accessible names.
  • Sheets, dialogs and menus use correct semantics.
  • Selected/expanded states are programmatically exposed.
