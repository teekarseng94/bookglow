Merchant Portal Upgrade Blueprint

The page-by-page operational blueprint for refining Bookglow’s existing merchant workspace across desktop, tablet and mobile while preserving all current business behavior.

Make the day understandable, keep context visible, and make every save, status and payment accountable.

01 · Mandate and current portal truth

Upgrade the existing merchant portal page by page.

Book 2 governs the merchant operating workspace in apps/merchant-portal. The latest archive already contains redesigned shell and page components, so implementation begins with an audit of what is complete, what is partial and what remains visually inconsistent—not a blank-screen rebuild.

Preserve

Routes, Firebase services, Firestore subscriptions, page props, role behavior, POS/CRM/inventory/staff/reporting handlers and deployment targets.

Improve

Hierarchy, density, mobile layouts, forms, drawers, sticky actions, loading/error states and shared component consistency.

Do later

Supabase cutover, full provisioning, billing and any operational feature that does not already exist.

The merchant portal is not a dashboard gallery. It is the place where time, customers, staff, inventory and money become accountable records.

05 · Role and permission experience

Current roles are admin and cashier; staff is not yet a login role.

RoleCurrent accessUX rule
AdminFull merchant navigation and configurationShow all supported modules; dangerous actions still require confirmation.
CashierPOS, Member, Menu/Catalog and Sales ReportsHide unavailable modules and redirect protected URLs safely to POS.
Super adminPlatform-level workspace oversightClearly distinguish platform context from merchant context.
Staff entityOperational profile, services, schedule and commissionDo not imply that each staff record can log in until an access model exists.
  • Permission errors explain the role limitation.
  • Never flash admin navigation before role resolution.
  • Remote-view or outlet override states are visibly labelled.
  • Future permissions should extend the current boundary rather than bypassing it in page code.

14 · Settings and integrations

Group configuration by business meaning, not code ownership.

Business

Outlet identity, contact, address, currency/locale and operating hours.

Booking

Booking path, public profile, services/team visibility, operating rules and preview.

Operations

Payment methods, receipt, points/credit, appointment behavior and other portal settings.

Access

Role and team controls where currently supported.

Integrations

Setmore sync, API keys, webhooks and external connection status.

Danger

Disable/archive/destructive actions with exact consequences.

Mobile requirements

  • Operating hours use one compact row per day: day, start–end and open/closed.
  • Settings sections save independently when safe.
  • Saving, saved and failed states remain visible.
  • Booking settings link to a real customer-site preview.
  • Integration cards show status, last sync/error and reconnect/disconnect action.

The current settings components already include navigation, section wrappers, operating-hour rows, save bar and save status. Align the large Settings.tsx container around them.

17 · Operational state system

Use the same state grammar across all pages.

StatePattern
Initial loadingLayout-preserving skeleton and current context.
RefreshingKeep existing data visible and show non-blocking progress.
EmptyExplain why and provide the correct first action.
Filtered emptyClear filters or change date; do not suggest creating duplicate data.
Save in progressDisable duplicate action and retain form context.
Save failureSpecific error and retry; do not close editor.
Permission blockExplain role limitation.
ConflictPreserve work and show safe reconciliation.
Unknown resultDo not invite duplicate sale/booking submission.

Standardise through current shared UI primitives: LoadingSkeleton, EmptyState, ErrorState, Alert, SaveStatus, ConfirmationDialog, Toast and ErrorBoundary.

19 · Logic preservation rules

No visual task may silently change business behavior.

  • Keep useFirestoreData subscriptions and update handlers unless the task explicitly targets data logic.
  • Keep appointment-to-POS handoff and transaction completion behavior.
  • Keep customer points, credit and outstanding transaction services intact.
  • Keep staff commissions and role locks intact.
  • Keep voucher service behavior intact.
  • Keep Setmore sync and external integration contracts intact.
  • Keep Firebase identifiers, outlet scoping and role resolution intact.
  • Do not replace a page wholesale without first mapping callbacks, local state and side effects.
Large-file rule: extracting visual components is encouraged; moving or rewriting business logic only to achieve a cleaner folder is prohibited during the UI phase.

23 · Book 2 completion definition

The portal upgrade is accepted when merchants can work faster without relearning the product.

  • Every existing operational route retains its behavior.
  • Admin and cashier experiences are correct and visibly distinct.
  • Schedule, POS, CRM, catalog, staff and reports work at phone widths.
  • No routine page requires horizontal scrolling.
  • All edits have visible save/progress/failure states.
  • States and statuses use one shared grammar.
  • Real Bookglow records—not demo screenshots—drive product proof for the platform site.
  • No Supabase or new Firebase architecture is introduced during visual implementation.
