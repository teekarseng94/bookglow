Visual Design & Merchant-Theming System

The semantic visual language for the existing customer and merchant applications, with mobile-first density and governed merchant identity.

01 · Design mandate

Apply one governed visual system to the current live components.

Volume III translates the approved experience into reusable visual foundations. It does not introduce a new booking component tree or alternate application.

Implementation boundary: restyle and recompose the current live screens. Never recreate removed or parallel component systems.
02 · Dual-surface design

Customer calm and merchant efficiency share foundations but not density.

SurfaceVisual goalDensity
Customer storefront and bookingTrustworthy, merchant-owned, guided and calm.Moderate; one decision at a time.
Merchant portalFast, compact, operational and predictable.High but structured.
Authentication and marketingClear, credible and product-aligned.Moderate with concise proof.
03 · Token foundation

Use semantic roles before page-level styling.

Token layerExamplesRule
FoundationNeutral palette, spacing, type sizes, radii, borders, shadows.Defined centrally.
Semantictext-primary, surface-page, action-primary, state-danger, focus-ring.Components consume roles, not raw values.
Componentcard-padding, sticky-action-height, calendar-day-size.Use only when a component needs a stable contract.
Merchant themetheme-action, theme-soft, theme-border.Applied only to governed customer-facing roles.
04 · Colour system

Neutral surfaces carry the product; accent marks action and identity.

  • Warm-neutral page and card surfaces.
  • Dark neutral text for transactional clarity.
  • Bookglow accent for portal primary actions and selected states.
  • Merchant accent only on customer primary actions, selection and small identity details.
  • Success, warning, danger and information colours retain fixed semantic meaning.
  • Never use merchant colour for errors, all body text or full-page transactional backgrounds.

07 · Spacing and density

A 4-pixel rhythm keeps both booking and operations calm.

ContextRule
Mobile page edge16 px.
Tablet page edge24 px.
Desktop page edge32 px.
Dense row gap8–12 px.
Standard card padding16–20 px.
Large section separation40–64 px.
Touch target44 px preferred.
Density principle: reduce wasted vertical space by grouping related metadata, not by shrinking text below readable sizes.
08 · Shape and elevation

Use soft geometry and one clear containment level.

  • 8 px for compact badges.
  • 10–12 px for fields, buttons and slots.
  • 16–18 px for cards and panels.
  • 24–28 px for sheets and large temporary surfaces.
  • Borders do most containment work; shadows remain restrained.
  • Avoid card inside card inside card.
09 · Imagery

Show real merchants, staff and services without fabricating trust.

  • Use responsive image sizes and deliberate crops.
  • Never use random stock staff faces as operational data.
  • Provide stable logo and cover fallbacks.
  • Keep text out of uploaded cover images where possible.
  • Do not allow oversized mobile imagery to hide the first useful action.

13 · Navigation design

Navigation reflects task priority, role and current location.

  • Desktop uses grouped sidebar navigation.
  • Mobile uses a small set of primary destinations plus a More sheet.
  • The active page and outlet/user context remain visible.
  • Role permissions control both navigation and actions.
  • Do not expose internal route names as labels.
14 · Responsive system

Components recompose; they do not simply shrink.

BreakpointComposition
0–599 pxSingle column, compact header, sticky actions and full-width sheets.
600–899 pxSingle or balanced two-column tasks with touch-first controls.
900–1199 pxPrimary content with optional detail or summary rail.
1200 px+Maximum-width layout; no uncontrolled stretching.
15 · Accessibility

Accessible behavior is part of every component contract.

  • WCAG-aligned contrast.
  • 44×44 px preferred targets.
  • Keyboard-complete primary workflows.
  • Visible focus.
  • Semantic headings and labelled controls.
  • State information conveyed beyond colour.
  • Reduced-motion support.
  • Readable error and consent text.
16 · Current-code mapping

Apply the visual system through the files that already exist.

AreaTreatment
Global styles/tokensCentralise semantic variables and base accessibility defaults.
Shared UI primitivesCreate only reusable presentational components.
Existing pagesKeep state, effects, handlers and service calls in their current containers.
Existing modals/sheetsRestyle or extract presentation without replacing invocation logic.
Customer route compositionUse the current live route and components as the only implementation.
Merchant pagesRetrofit page by page in operational order.
17 · Anti-patterns

Visual choices that weaken Bookglow.

1

Full-page accent colour

Large saturated backgrounds weaken transactional clarity.

2

Nested cards

Repeated containment wastes mobile space and obscures hierarchy.

3

Oversized mobile headers

First actions disappear below decorative content.

4

Colour-only selection

Users cannot reliably identify state.
